# Выбор и настройка мониторинга в системе

## Что видно на схеме

Если пройтись по C4-диаграмме контейнеров с вопросом «что тут мерить», получается так:
- три API (Shop API, CRM API, MES API) обслуживают запросы людей и партнёров. Для них важны число запросов, ошибки и задержка;
- MES API ещё и считает стоимость. Это долгая работа, она делит ресурсы с дашбордом операторов и с запросами партнёров;
- RabbitMQ — единственный путь статусов между MES и CRM. Если он копит сообщения или складывает их в dead-letter, заказы застревают;
- Shop DB общая для магазина и CRM, MES DB одна на запись и чтение. Обе работают в одном экземпляре, и их насыщенность — первый кандидат в узкие места;
- S3 с 3D-файлами растёт вместе с заказами;
- каждое приложение и база — один инстанс на EC2 или managed, так что важна и загрузка самих машин.

Отсюда и разбиение ниже: RED для API, USE для ресурсов и отдельно бизнес-метрики заказов.

## Мотивация

Сейчас о проблемах с заказами мы узнаём от клиентов, продавцов и операторов, и обычно через недели после того, как заказ застрял. Яндекс Метрика показывает только поведение людей на сайте. Заказы, которые приходят через API от продавцов, в ней не видны вообще, а это сейчас основной рост и основной источник жалоб.

Мониторинг даст компании вот что:

- узнавать о проблеме раньше клиента. Алерт на рост сообщений в dead-letter RabbitMQ или на ошибки MES API приходит дежурному через минуты, а не через жалобу менеджеру через месяц. Это прямо про потерянные контракты;
- понимать, где узкое место: расчёт стоимости, очередь, база MES или сам API. Без этого любые доработки делаются наугад, и на них уходят спринты;
- планировать мощности. Нагрузка растёт на 100 заказов в месяц плюс скачки от партнёров. По графикам видно, когда кончится один инстанс MES API или база, и можно добавить ресурсы до падения, а не после;
- проверять релизы. Дашборд смотрим при каждой выкладке: если после релиза выросли ошибки или задержка, откатываем сразу;
- иметь цифры для разговора с партнёрами по API: сколько запросов, какая задержка, какая доля ошибок по каждому клиенту.

По затратам это открытый стек (Prometheus, Grafana) и несколько дней работы DevOps и разработчиков на подключение библиотек. Один потерянный крупный контракт стоит дороже.

## Выбор подхода к мониторингу

Для разных частей системы беру разные подходы.

RED для трёх API: Shop API, CRM API, MES API. Это сервисы, которые работают по запросам пользователей и партнёров. Нам важно, сколько запросов приходит (Rate), сколько из них падает (Errors) и сколько они длятся (Duration). Это ровно то, что чувствуют клиенты, продавцы и операторы. Все три показателя снимаются одной гистограммой длительности запросов с метками.

USE для ресурсов: инстансы EC2 под API, базы Shop DB и MES DB, RabbitMQ, хранилище S3. Эти ресурсы деградируют при нагрузке, и у них важны загрузка (Utilization), насыщенность (Saturation, очереди и ожидание) и ошибки (Errors). Для RabbitMQ насыщенность — это очередь непрочитанных сообщений и сообщения без подтверждения, для базы — занятые соединения и память.

Четыре золотых сигнала целиком не беру. Задержку, трафик и ошибки по API закрывает RED, насыщенность закрывает USE по ресурсам. Отдельный третий набор метрик дублировал бы первые два.

Сверху добавляю бизнес-метрики по заказам. Ни RED, ни USE не покажут заказ, который тихо висит в статусе `PRICE_CALCULATED` третью неделю, а это и есть главная боль.

## Метрики

Во всех метриках API есть стандартные метки Prometheus `instance` и `job`. Ниже перечислены дополнительные метки.

Общее правило по меткам. Путь пишем шаблоном (`/orders/{id}`), а не реальным URL, иначе число рядов взлетит. Идентификатор покупателя магазина в метки не ставлю: покупателей много, и это персональные данные. Идентификатор партнёра (`client_id`) ставлю только в MES API: партнёров десятки, и разбивка по ним нужна для лимитов и для разговора с ними.

### API (RED)

| № | Метрика | Зачем | Метки |
|---|---|---|---|
| 3 | RPS Shop API | Rate: нагрузка от магазина, пики и рост, планирование мощности | `method`, `route`, `status_code` |
| 4 | RPS CRM API | Rate: нагрузка от продавцов и от обработки сообщений из очереди | `method`, `route`, `status_code` |
| 5 | RPS MES API | Rate: главный по нагрузке API, сюда ходят и операторы, и партнёры | `method`, `route`, `status_code`, `client_id` |
| 8 | RPS per user MES API | Сколько запросов шлёт каждый партнёр, кто упирается в лимит. Делаю не отдельной метрикой, а меткой `client_id` на метрике 5 | см. 5 |
| 19 | Latency Shop API | Duration: скорость сайта для покупателя, загрузка 3D-файлов | `method`, `route`, `status_code` |
| 20 | Latency CRM API | Duration: скорость работы продавцов | `method`, `route`, `status_code` |
| 21 | Latency MES API | Duration: в том числе главная страница MES, на которую жалуются операторы, и запросы партнёров | `method`, `route`, `status_code`, `client_id` |
| 28 | HTTP 500 Shop API | Errors: доля ошибок магазина | `route` |
| 29 | HTTP 500 CRM API | Errors: доля ошибок CRM | `route` |
| 30 | HTTP 500 MES API | Errors: доля ошибок MES, отдельно по партнёрам | `route`, `client_id` |
| 35 | Kb received Shop API | Размер входящих данных: 3D-файлы бывают большими, по ним видно, что упирается в сеть или загрузку | `route` |

Метрики 3–5, 19–21 и 28–30 снимаю одной гистограммой `http_server_requests_seconds` на каждый API. `_count` с меткой `status_code` даёт rate и ошибки, `_bucket` даёт перцентили задержки. Ошибкой считаю все ответы 5xx, а не только 500. Для MES API отдельно смотрю 429: это отказы по лимиту, и их рост значит, что партнёр шлёт больше квоты.

Что из списка не беру:
- 6, 7 (RPS per user магазина и CRM): покупателей магазина много, метка по пользователю раздует число рядов и запишет ПДн в метрики. Продавцов CRM мало, и их нагрузка неинтересна;
- 25–27 (HTTP 200): это та же гистограмма с `status_code="200"`, отдельная метрика не нужна;
- 31: дубль метрики 28;
- 32–34 (одновременные сессии): для RED не нужны, а нагрузку уже показывает RPS. Если понадобится бизнес-аналитика по сессиям магазина, её даёт Яндекс Метрика;
- 36–40 (Kb sent и received для CRM и MES): трафик там небольшой, проблем с сетью в жалобах нет. Вернусь к ним, если метрики задержки укажут на сеть.

### Ресурсы (USE)

| № | Метрика | Зачем | Метки |
|---|---|---|---|
| 9, 10, 11 | CPU % Shop, CRM, MES API | Utilization инстанса. Для MES особенно: расчёт стоимости грузит CPU и тормозит всё остальное | `service`, `instance` |
| 12, 13, 14 | Memory Utilisation Shop, CRM, MES API | Utilization памяти, утечки, риск падения процесса | `service`, `instance` |
| 15, 16 | Memory Utilisation Shop DB, MES DB | Utilization памяти базы: если кеш базы не помещается, растут чтения с диска и тормозит дашборд | `db` |
| 17, 18 | Connections Shop DB, MES DB | Saturation базы: упёрлись в `max_connections`, и новые запросы ждут или падают. В Shop DB ходят и магазин, и CRM | `db`, `client_app` |
| 22 | Size of S3 storage | Utilization хранилища 3D-файлов, рост вместе с заказами, планирование затрат | `bucket` |
| 23, 24 | Size Shop DB, MES DB | Utilization диска базы, прогноз, когда кончится место | `db` |
| 1 | Dead-letter messages RabbitMQ | Errors брокера: каждое сообщение в DLX — заказ, который не дошёл до CRM или MES. Главная метрика по потерям | `queue` |
| 2 | Messages in flight RabbitMQ | Saturation: сообщения отданы обработчику, но не подтверждены. Если число растёт, обработчик завис | `queue` |

Свои метрики сверх списка:

| Метрика | Зачем | Метки |
|---|---|---|
| CPU % Shop DB, MES DB | Utilization базы: тяжёлые запросы дашборда видны сразу | `db` |
| Messages ready в очередях RabbitMQ | Saturation: очередь растёт, значит потребитель не успевает | `queue` |
| Consumers на очередь RabbitMQ | Errors: потребитель отвалился, а очередь копится молча | `queue` |
| Длительность расчёта стоимости в MES (гистограмма) | Расчёт занимает от 2–3 до 30 минут, нужно видеть распределение и как его меняет сложность модели | `source` (`shop`, `api`) |
| Число заказов в очереди на расчёт и время ожидания | Saturation расчёта: если ожидание растёт, нужны ещё воркеры. Метрика появится вместе с очередью расчёта (инициатива И5 из задания 1), до этого смотрим длительность расчёта и CPU MES API | `source` |

### Заказы (бизнес-метрики)

| Метрика | Зачем | Метки |
|---|---|---|
| Переходы статусов заказа, счётчик | Сколько заказов входит в каждый статус в час, видно, где поток обрывается | `status`, `source` (`shop`, `api`), `system` (`shop`, `crm`, `mes`) |
| Число заказов в статусе дольше нормы, gauge | Главная метрика для бизнеса: застрявшие заказы. Нормы по статусам ниже | `status`, `source` |

Эту пару считает небольшой экспортёр, который раз в минуту делает запрос к MES DB и Shop DB. Он смотрит текущий статус и время последнего перехода, поэтому видит и заказ, который висит несколько месяцев. Это единственный источник алерта о застрявших заказах. Трейсинг в задании 3 его не дублирует, а ловит другое: сообщение отправлено, но не обработано. Номера заказов и данные клиентов в метки не попадают, конкретные заказы ищем через трейсинг (задание 3) и логи (задание 4).

Нормы времени в статусе (стартовые, через месяц уточним по данным; эти же цифры используются в заданиях 1 и 3):

| Переход | Норма | Откуда |
|---|---|---|
| `SUBMITTED` → `PRICE_CALCULATED` | 40 минут | самый долгий расчёт 30 минут плюс до 10 минут в очереди |
| `PRICE_CALCULATED` → `MANUFACTURING_APPROVED` | 1 рабочий день | продавец подтверждает заказ |
| `MANUFACTURING_APPROVED` → `MANUFACTURING_STARTED` | 2 рабочих дня | оператор берёт заказ |
| `MANUFACTURING_STARTED` → `SHIPPED` | 18 дней | чтобы уложиться в обещанные три недели |
| `SHIPPED` → `CLOSED` | 10 дней | доставка и сообщение транспортной компании |

## План действий

1. Развернуть Prometheus и Alertmanager на отдельной ВМ в Yandex Cloud, рядом Grafana. Хранение метрик 30 дней, для долгих трендов можно потом добавить VictoriaMetrics.
2. Shop API и CRM API: подключить Spring Boot Actuator и `micrometer-registry-prometheus`, открыть `/actuator/prometheus` только во внутренней сети, включить гистограммы `http.server.requests`.
3. MES API: подключить `prometheus-net` (ASP.NET Core), отдать `/metrics`, добавить метку `client_id` для запросов партнёров и гистограмму длительности расчёта стоимости.
4. На все EC2 поставить `node_exporter` (CPU, память, диск).
5. RabbitMQ: включить плагин `rabbitmq_prometheus` (очереди, ready, unacked, consumers, DLX).
6. Managed PostgreSQL и S3: забирать метрики из Yandex Monitoring через его Prometheus-совместимую выгрузку, при нехватке добавить `postgres_exporter` для соединений по приложениям.
7. Написать экспортёр бизнес-метрик заказов (переходы статусов и застрявшие заказы).
8. Добавить все источники в `scrape_configs` Prometheus.
9. Собрать дашборды в Grafana: RED по каждому API с переменной `service`, USE по ресурсам, заказы по статусам. Добавить аннотации релизов.
10. Настроить алерты в Alertmanager (пороги ниже) и каналы: Telegram-чат дежурных, почта, для критичных автозвонок. Описать, кто дежурит. Alertmanager поднять в двух экземплярах и завести постоянно срабатывающий watchdog-алерт во внешний сервис: если он перестал приходить, значит, лёг сам мониторинг.
11. Через месяц пересмотреть пороги по реальным данным.

## Дополнительно: пороги насыщенности и реакция

Числа ниже стартовые, исторических данных пока нет. Через месяц сбора их надо подправить.

| Показатель | Порог | Почему такой | Что происходит |
|---|---|---|---|
| Сообщения в DLX RabbitMQ | больше 0 за 5 минут | каждое сообщение в DLX — потерянный переход статуса | алерт дежурному разработчику и автоматический тикет с именем очереди, разобрать и переотправить в тот же день |
| Messages ready в очереди | растёт 15 минут подряд или больше 1000 | очередь не разбирается, заказы встают | алерт дежурному, проверить потребителя, при живом потребителе добавить экземпляр обработчика |
| Consumers на очередь | 0 дольше 2 минут | обработчик упал, очередь копится молча | автозвонок дежурному |
| Ожидание расчёта стоимости | p95 больше 10 минут | вместе с 30 минутами самого расчёта это уже норма 40 минут, дальше заказы её нарушают | добавить воркер расчёта (после И5 автоматически), до этого тикет на ручное масштабирование |
| CPU инстанса API | больше 80% дольше 10 минут | выше 80% начинает расти задержка, а запас нужен на скачки от партнёров | алерт в чат, тикет на увеличение ресурсов или второй инстанс |
| Память инстанса API | больше 85% дольше 10 минут | дальше риск падения процесса по памяти | алерт в чат, тикет, разбор утечки |
| Соединения к БД | больше 80% от `max_connections` | на 100% новые запросы получают ошибку | алерт в чат, проверить пулы соединений приложений, увеличить класс хоста БД |
| Диск БД и размер S3 | больше 80% выделенного | managed-базе нужен запас, увеличение диска делается не мгновенно | тикет DevOps, увеличить диск в течение недели |
| Ошибки 5xx API | больше 1% запросов за 5 минут | при росте заказов даже 1% это десятки потерянных действий | алерт дежурному, при совпадении с релизом откат |
| Задержка главной страницы MES | p95 больше 2 секунд за 10 минут | операторы теряют деньги из-за задержки | алерт в чат команды MES |
| 429 по партнёру | больше 5% его запросов | партнёр уперся в квоту | письмо продакт-менеджеру и партнёру, пересмотреть квоту |
| Заказы в статусе дольше нормы | больше 0 | это ровно та ситуация, из-за которой уходят клиенты | для `SUBMITTED` и `PRICE_CALCULATED` сразу алерт дежурному (обычно это технический сбой). Для остальных статусов тикет в поддержку со ссылкой на дашборд и раз в день сводка руководителю продаж и производства |
