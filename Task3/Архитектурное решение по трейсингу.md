# Архитектурное решение по трейсингу

## Анализ: что покрываем трейсингом и где заказ может сломаться

Заказ проходит через три приложения и очередь. Трейсингом покрываю:

- Shop API: создание заказа, загрузка 3D-файла в S3, смена статусов `INITIATED`, `FILE_UPLOADED`, `SUBMITTED`;
- CRM API: забирает новые заказы, публикует и читает сообщения RabbitMQ, переводит заказ в `MANUFACTURING_APPROVED` и `CLOSED`;
- MES API: приём заказов от партнёров через API, расчёт стоимости, все производственные статусы от `PRICE_CALCULATED` до `SHIPPED`;
- RabbitMQ: сам брокер span'ы не пишет, но контекст трейса передаётся в заголовке `traceparent` каждого сообщения. Поэтому публикация и обработка сообщения попадают в один трейс.

На схеме эти системы обведены красной пунктирной рамкой.

Фронтенды (магазин, CRM, MES) на первом этапе не трейсим, об этом в «Компромиссах».

Где заказ может сломаться или зависнуть:

1. Магазин сохранил заказ в `SUBMITTED`, а CRM его не забрала: ошибка при чтении Shop DB или при публикации в очередь.
2. Сообщение о новом заказе ушло в RabbitMQ, но MES его не обработала: упал обработчик, сообщение попало в DLX или потерялось без подтверждения.
3. Расчёт стоимости в MES. Он идёт от 2–3 до 30 минут, может упасть на сложной модели, не найти файл в S3 или встать в очередь за заказами партнёров.
4. `PRICE_CALCULATED` посчитан в MES, но сообщение не дошло до CRM, и продавец не видит заказ для подтверждения.
5. Заказ от партнёра через API: MES создала его у себя, а сообщение в CRM не дошло, и в CRM заказа нет совсем.
6. `MANUFACTURING_APPROVED` из CRM не дошёл до MES, и оператор заказ не видит.
7. Заказ отправлен (`SHIPPED`), но сообщение от транспортной компании не пришло, и заказ не закрывается.

Данные, которые попадают в трейс:

| Данные | Где | Зачем |
|---|---|---|
| `trace_id`, `span_id` | все span'ы | склеить путь запроса и сообщения |
| `service.name`, `deployment.environment`, версия сервиса | resource всех сервисов | понять, какая система и какая версия |
| `order.id` | все span'ы, где есть заказ | главный ключ поиска: найти все трейсы заказа |
| `order.status.from`, `order.status.to` | span смены статуса | видеть переходы и где они обрываются |
| `order.source` (`shop` или `api`) | все span'ы заказа | отличать B2C и партнёрские заказы |
| `partner.id` | span'ы MES API от партнёров | разбирать жалобы конкретного партнёра |
| `messaging.destination` (очередь), `messaging.message.id`, номер попытки доставки | span'ы публикации и обработки RabbitMQ | найти потерянное или повторное сообщение |
| длительность расчёта, число полигонов модели, размер файла | span расчёта стоимости в MES | понять, почему расчёт долгий |
| `http.route`, `http.response.status_code`, ошибка и её тип | span'ы HTTP | где упал запрос |
| идентификатор оператора или продавца (внутренний id сотрудника) | span'ы действий в CRM и MES | кто взял заказ или подтвердил его |

В трейс не пишем ФИО, телефоны, почту, адреса доставки, содержимое 3D-файлов, токены и ключи API. Трейсы смотрит поддержка и разработка, им эти данные не нужны. Идентификатор покупателя в трейс тоже не пишу: по `order.id` его при необходимости найдёт CRM. Внутренние id сотрудников и партнёров в трейсах остаются. Это псевдонимизированные данные: по ним человека определяют только через справочники CRM и MES. Категорию считаю по самому чувствительному полю, поэтому трейсы относятся к конфиденциальным данным. Отсюда и ограничения доступа в разделе «Безопасность».

## Мотивация

Сейчас заказ, который завис между системами, никто не видит, пока клиент не пожалуется. Чтобы понять, что с ним случилось, разработчики по очереди смотрят три базы и вспоминают, что могло пойти не так. Компания уже потеряла несколько крупных контрактов именно из-за таких заказов.

Трейсинг даёт:
- путь любого заказа по системам в одном месте: ввёл `order.id` в Jaeger и видишь, в каком статусе он и на каком шаге остановился;
- место и причину сбоя: какой сервис вернул ошибку, какое сообщение не обработано, сколько длился расчёт;
- данные для дальнейших доработок: где реально тратится время, а не где нам кажется.

Метрики, на которые повлияет внедрение:

1. Время обнаружения проблемы с заказом (MTTD). Сейчас это недели, жалоба клиента. Цель: минуты, алерт о потерянном сообщении из раздела про мониторинг прохождения заказа.
2. Время разбора инцидента с заказом (MTTR). Сейчас несколько часов на поиск по трём системам. Цель: до 30 минут, потому что путь заказа виден сразу.
3. Доля заказов, застрявших в статусе дольше нормы. Трейсинг показывает, где именно, и после исправлений доля должна падать.
4. Доля заказов, выполненных в обещанный срок (три недели). Это бизнес-метрика, на которую в итоге работает всё остальное.
5. Число жалоб партнёров API на потерянные заказы. Сейчас ежедневные, цель: единичные. По `partner.id` поддержка быстро отвечает партнёру, что с его заказом.

Числовые цели здесь — допущения, точку отсчёта даст первый месяц работы трейсинга.

## Предлагаемое решение

Стек: OpenTelemetry для сбора, Jaeger для хранения и просмотра, OpenSearch как хранилище трейсов.

Почему так. OpenTelemetry — открытый стандарт с готовой инструментацией для Spring Boot и .NET, то есть для всех трёх наших бэкендов. Контекст передаётся по стандарту W3C Trace Context в HTTP и в заголовках сообщений RabbitMQ. Jaeger умеет искать трейсы по тегам (`order.id`), принимает OTLP напрямую и бесплатен. OpenSearch я и так беру под логи (задание 4), один кластер с отдельными индексами проще поддерживать одному DevOps.

Что внедряем и дорабатываем:

1. Shop API и CRM API (Spring Boot): подключаем OpenTelemetry Java agent. Он сам снимает span'ы HTTP, JDBC, Spring AMQP, а значит и `traceparent` в сообщениях RabbitMQ без правки кода. Дописываем вручную span смены статуса и атрибуты `order.id`, `order.status.*`, `order.source`.
2. MES API (C#): подключаем OpenTelemetry .NET (ASP.NET Core, HttpClient, Npgsql, RabbitMQ.Client). Исходники MES у компании есть, поэтому дописываем span расчёта стоимости с его атрибутами и передачу контекста в сообщениях, если клиент RabbitMQ в MES не инструментируется автоматически.
3. OpenTelemetry Collector, два инстанса за внутренним балансировщиком. Принимает OTLP от трёх API, батчит, вычищает запрещённые атрибуты (страховка, если ПДн всё-таки попали в span), и отдаёт в Jaeger. Healthcheck-запросы отбрасываем сразу. Остальное на старте не сэмплирую, храним все span'ы: объём небольшой, а пропущенный трейс потерянного заказа обидно терять. Если объём вырастет, включим хвостовое сэмплирование (все трейсы с `order.id` и с ошибками, остальное на 10%). Тогда перед ним понадобится слой Collector с `loadbalancing` exporter по `trace_id`, чтобы все span'ы трейса попадали на один инстанс.
4. Jaeger (collector + query) с хранилищем в OpenSearch. Индекс трейсов на каждый день, хранение 30 дней. Трейсы нужны для разбора шагов: где упал вызов, где потерялось сообщение. Такие случаи разбирают по свежим следам, после алерта. Историю заказа, который висит месяцами, держат другие источники: текущий статус лежит в базе, а события смены статуса — в отдельном индексе логов на 180 дней (задание 4).
5. Секреты: TLS-ключ Collector и учётная запись Jaeger в OpenSearch лежат в Yandex Lockbox, а не в конфигах.

Важная деталь про долгие заказы. Жизненный цикл заказа — недели, и тянуть один трейс на три недели неправильно: span не может висеть открытым так долго. Поэтому каждый шаг (запрос пользователя, обработка сообщения, расчёт) — свой трейс, а связывает их атрибут `order.id`. Поиск в Jaeger по `order.id=...` показывает все трейсы заказа по порядку. Внутри шага, например «MES посчитала цену → сообщение → CRM обновила статус», трейс один, контекст переходит через RabbitMQ.

Схема: [c4-tracing.drawio](c4-tracing.drawio). Это диаграмма контейнеров из условия, новые элементы и связи на ней красные, системы под трейсингом обведены красной пунктирной рамкой.

### Дополнительно: автоматический мониторинг прохождения заказа и алертинг

Мало уметь найти заказ, когда пожаловались. Нужно, чтобы система сама замечала заказ, который застрял между системами.

Разделение с мониторингом из задания 2. Заказы, которые сидят в статусе дольше нормы, считает экспортёр по текущему состоянию в базах (задание 2). Он видит и заказ, который висит месяцами, и нормы по статусам заданы там же. Трейсы для этого не подходят, они хранятся 30 дней. Из трейсов я беру то, чего база не покажет: где именно оборвалась цепочка между системами.

Что добавляю (на схеме зелёным):

1. В OTel Collector включаю `spanmetrics`. Он считает по span'ам число вызовов, ошибки и длительность каждого шага, например «расчёт стоимости» или «обработка сообщения PRICE_CALCULATED в CRM», с метками сервиса и операции. Prometheus из задания 2 забирает эти метрики.
2. Небольшой сервис Order flow monitor, запускается раз в 5 минут. Он берёт из хранилища трейсов span'ы публикации сообщений о заказах за последний час и ищет для каждого парный span обработки на стороне получателя с тем же `trace_id`. Если сообщение отправлено больше 5 минут назад, а обработки нет, значит, оно потерялось или застряло в очереди. Сервис отдаёт метрику потерянных сообщений с метками очереди и типа события, а номера заказов пишет в свой лог. В метрику уходят только количества, чтобы не раздувать Prometheus.
3. Правила в Alertmanager:
   - есть потерянное сообщение: алерт дежурному в Telegram сразу, в тексте очередь, тип события и ссылка на поиск в Jaeger;
   - доля ошибок шага по `spanmetrics` больше 1% за 10 минут: алерт дежурному;
   - нет ни одного span'а обработки в очереди при живом потоке публикаций дольше 5 минут: автозвонок дежурному, обработчик лёг.
4. Дежурный (роль «Поддержка» с основной схемы) открывает ссылку из алерта, видит трейсы заказа и место, где он остановился, и переотправляет сообщение.

Схема с этими элементами: [c4-tracing-alerting.drawio](c4-tracing-alerting.drawio). Новое здесь выделено зелёным, элементы основного решения остались красными.

## Компромиссы

- Фронтенды (магазин, CRM, MES в браузере) на первом этапе не трейсим. Браузерный трейсинг требует отдельной доработки, а заказы теряются между бэкендами. Вернёмся к нему, если понадобится разбирать медленную загрузку страниц, например дашборда MES.
- RabbitMQ и managed PostgreSQL сами span'ы не пишут. Видим только вызовы со стороны клиентов: сколько шла публикация, сколько запрос в базу. Что происходит внутри брокера, показывает мониторинг (задание 2), а не трейсинг.
- MES купленная. Исходники есть, но каждая наша правка в её коде усложняет обновление от поставщика. Держу правки минимальными: инструментация через стандартные библиотеки и несколько ручных span'ов в расчёте и смене статусов. Если поставщик выпустит крупное обновление, правки придётся переносить.
- Шаги, которые делают люди (продавец подтверждает, оператор берёт заказ), трейсингом не меряются: между ними часы и дни без вызовов. Здесь полезнее метрика времени в статусе и алерт по застрявшим заказам из задания 2.
- Транспортная компания внешняя. Её систему мы не трейсим, видим только момент, когда CRM получила от неё сообщение. Если сообщение не пришло, трейсинг покажет только его отсутствие.
- Стоимость хранения. Храним все span'ы заказов 30 дней, при росте числа заказов растёт и объём OpenSearch. Если станет дорого, сократим срок для успешных трейсов и оставим 30 дней только для трейсов с ошибками.
- Трейсинг не заменяет логи. Он показывает, где случилась ошибка, а подробности смотрим в логе по тому же `trace_id` (задание 4).

## Безопасность

- Jaeger UI доступен только из корпоративной сети или через VPN, наружу не публикуется.
- Вход в Jaeger UI через корпоративную учётную запись (SSO через oauth2-proxy перед Jaeger Query). Пускаем только сотрудников с ролью «Поддержка» или «Разработка» и действующей учётной записью. При увольнении учётка блокируется, и доступ пропадает сам.
- Партнёры доступа к Jaeger не получают. Статус своего заказа они узнают через API.
- Collector принимает данные только по TLS и только из подсети приложений: это ограничено группами безопасности Yandex Cloud. Снаружи записать поддельные трейсы нельзя.
- TLS-ключ Collector и пароль Jaeger к OpenSearch хранятся в Yandex Lockbox, доступ к ним только у сервисных аккаунтов и DevOps.
- Персональные данные в трейс не пишем (список выше), Collector дополнительно вырезает атрибуты из запрещённого списка.
- Входы в Jaeger и запросы к OpenSearch пишутся в журнал аудита, он лежит вместе с логами безопасности (задание 4).

## Задание 3.1: MVP трейсинга с OpenTelemetry и Jaeger в Kubernetes

Конфигурации из репозитория курса лежат в [k8s/](k8s/). В `services.yaml` я добавил сервисам переменную `OTEL_EXPORTER_OTLP_ENDPOINT` с адресом коллектора Jaeger.

Сервисы написаны на Go и лежат в [services/](services/):
- `service-a` — сервис заказов. Метод `GET /` спрашивает цену у `service-b` и возвращает ответ;
- `service-b` — сервис расчёта стоимости. Метод `GET /price` считает цену и пишет отдельный span `calculate price`.

Оба используют OpenTelemetry SDK, HTTP-обработчики и клиент обёрнуты `otelhttp`. Контекст передаётся в заголовке `traceparent`, поэтому вызов `service-a` и вложенный вызов `service-b` попадают в один трейс. Span'ы уходят по OTLP/HTTP в `simplest-collector:4318`. В span'ах есть атрибут `order.id`, как в основном решении.

Запуск (команды из README курса, порядок тот же, выполнять из папки `Task3`):

```bash
cd Task3
minikube start --addons=ingress
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.13.3/cert-manager.yaml
kubectl create namespace observability
kubectl create -f https://github.com/jaegertracing/jaeger-operator/releases/download/v1.51.0/jaeger-operator.yaml -n observability
kubectl apply -f k8s/jaeger-instance.yaml

minikube image build -t service-a:latest services/service-a/
minikube image build -t service-b:latest services/service-b/
kubectl apply -f k8s/services.yaml

kubectl exec -it $(kubectl get pods -l app=service-a -o jsonpath='{.items[0].metadata.name}') -- wget -qO- "http://service-a:8080/?order_id=ORD-1042"
kubectl port-forward svc/simplest-query 16686:16686
```

Дальше открыть http://localhost:16686, выбрать сервис `service-a` и нажать Find Traces.

При проверке на minikube 1.37 оператор Jaeger 1.51 не поднялся: образ `gcr.io/kubebuilder/kube-rbac-proxy:v0.13.1` из его манифеста удалён из реестра. Помогла замена на копию из quay.io:

```bash
kubectl -n observability set image deploy/jaeger-operator kube-rbac-proxy=quay.io/brancz/kube-rbac-proxy:v0.13.1
```

Скриншот трейса: [jaeger-trace.png](jaeger-trace.png). Вызывал `service-a` с `?order_id=ORD-1042`. В трейсе 4 span'а из двух сервисов с одним `trace_id`: `GET /` и исходящий `HTTP GET` в `service-a`, `GET /price` и вложенный `calculate price` в `service-b`. У `calculate price` видны атрибуты `order.id` и `order.price`.
