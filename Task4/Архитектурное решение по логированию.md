# Архитектурное решение по логированию

## Анализ: какие логи и откуда собираем

Сейчас логи, если они есть, лежат на каждом EC2 отдельно. Разбор начинается с рассказа клиента: что он делал и когда. Собирать логи буду из систем, через которые проходит заказ (на схеме они обведены красной пунктирной рамкой):

- MES API: расчёт стоимости, заказы от партнёров через API, производственные статусы, назначение заказов операторам;
- CRM API: обмен сообщениями с MES, подтверждение заказа продавцом, закрытие заказа;
- Shop API: создание заказа покупателем, загрузка 3D-файлов, отправка заказа;
- RabbitMQ: обрывы соединений, переполнение очередей, сообщения в dead-letter.

Логи managed PostgreSQL (Shop DB, MES DB) подключаю вторым этапом через Yandex Cloud Logging. Из них нужны медленные запросы и ошибки, это пригодится для дашборда MES, но не для поиска потерянных заказов. Фронтенды пока не логируем: ошибки в браузере клиента в жалобах не фигурируют.

Все сервисы пишут логи в JSON в stdout. Общие поля каждой записи: `timestamp`, `level`, `service`, `env`, `version`, `trace_id`, `span_id`, `order_id` (если операция про заказ), `message`. Благодаря `trace_id` из лога можно сразу перейти к трейсу в Jaeger (задание 3), и наоборот.

### Логи уровня INFO

| Событие | Система | Что пишем |
|---|---|---|
| Создан заказ | Shop API, MES API (заказ от партнёра) | время, `order_id`, источник (`shop` или `api`), `partner_id` для заказов от партнёров |
| Смена статуса заказа | Shop API, CRM API, MES API | время, `order_id`, статус было и стало, система, кто сменил: покупатель (без идентификатора), id продавца или оператора, `partner_id` |
| Загружен 3D-файл | Shop API | время, `order_id`, ключ файла в S3, размер, число полигонов |
| Начат и закончен расчёт стоимости | MES API | время, `order_id`, число полигонов, длительность, рассчитанная цена |
| Опубликовано сообщение | CRM API, MES API | время, очередь, `message_id`, тип события, `order_id` |
| Обработано сообщение | CRM API, MES API | время, очередь, `message_id`, `order_id`, номер попытки, длительность обработки |
| Заказ назначен оператору | MES API | время, `order_id`, id оператора |
| Заказ подтверждён продавцом | CRM API | время, `order_id`, id продавца |
| Заказ закрыт | CRM API | время, `order_id`, способ: сообщение транспортной компании или вручную, кто закрыл |
| Запрос партнёра к API | MES API | время, `partner_id`, метод и маршрут, код ответа, длительность |
| Вход пользователя в CRM и MES | CRM API, MES API | время, id пользователя, роль, IP. Пишется в отдельный индекс безопасности |
| Старт и остановка сервиса | все | время, сервис, версия, окружение |

### Другие уровни

- WARN: повторная доставка сообщения, расчёт стоимости дольше 30 минут, ответ 429 партнёру по лимиту, неверный ключ API партнёра, неудачный вход в CRM или MES, запрос к БД дольше 1 секунды. Это ещё не сбой, но повод присмотреться, а серия таких записей уже сигнал.
- ERROR: исключение при обработке запроса или сообщения, сообщение ушло в DLX, расчёт упал, файл не найден в S3, ошибка записи статуса в БД. Каждая такая запись — заказ, у которого что-то не так.
- FATAL: сервис не может стартовать или работать дальше, например потеряно соединение с БД или брокером без восстановления. После FATAL процесс завершается, и его перезапускает systemd на EC2 (после переезда в Kubernetes это будет делать сам Kubernetes).
- DEBUG: на продакшне выключен. Включаем точечно для одного сервиса через конфиг на время разбора (до часа) и выключаем. На dev и release включён всегда.
- TRACE: только локально и на dev.

## Мотивация

Разбор каждой проблемы сейчас начинается с расспросов клиента и заканчивается поиском по трём системам. Это часы работы разработчиков и поддержки на каждое обращение, а обращений становится больше вместе с заказами от партнёров. Централизованные логи позволяют по `order_id` из жалобы за минуты увидеть, что происходило с заказом во всех системах и на какой ошибке он остановился. Логи и трейсинг дополняют друг друга: трейс показывает, где сломалось, лог объясняет почему.

Метрики, на которые повлияет внедрение:

1. Время разбора обращения (MTTR). Сейчас часы, цель до 30 минут.
2. Доля обращений, разобранных без уточнений у клиента. Цель больше 80%.
3. Часы поддержки и разработки на разбор инцидентов в месяц. Освобождённое время уходит на инициативы из задания 1.
4. Время обнаружения ошибок после релиза. Рост ERROR видно в первые минуты, и релиз можно откатить, а не ждать жалоб.
5. Число повторных инцидентов одного типа. По логам видно, что ошибка массовая, и её чинят один раз, а не разбирают каждый случай.

Числовые цели здесь допущения, базу даст первый месяц сбора.

### Что подключаем первым

Логирование и трейсинг всех систем сразу команда не потянет: в ней один DevOps и по два бэкенд-разработчика на Java и C#. Порядок для обоих решений один:

1. MES API. Здесь больше всего боли: долгий расчёт стоимости, заказы от партнёров, тормоза у операторов, и половина статусов меняется здесь. Плюс через MES API ходят партнёры, а их жалобы стоят компании контрактов.
2. CRM API и RabbitMQ. Это вторая сторона интеграции, где по всем признакам теряются сообщения. Без неё логи MES покажут только половину пути.
3. Shop API. Начало пути B2C-заказа, жалоб по нему меньше. Spring Boot подключается быстро, тем же способом, что CRM API.
4. Логи managed PostgreSQL через Yandex Cloud Logging.
5. Фронтенды, если понадобятся.

## Предлагаемое решение

Стек: Fluent Bit для сбора, Yandex Managed OpenSearch для хранения и поиска, OpenSearch Dashboards для просмотра и алертов. Сравнение с ELK, Splunk и Loki — в дополнительном разделе в конце.

Компоненты:

1. Логирование в приложениях. Spring Boot (Shop API, CRM API): Logback с JSON-энкодером, `trace_id` и `span_id` подставляет OpenTelemetry agent из задания 3. MES API (C#): Serilog с JSON-форматом и обогащением из `Activity` (там те же `trace_id` и `span_id`). Маскирование ПДн делается прямо в логгере.
2. Fluent Bit агентом на каждом EC2 (при переезде в Kubernetes — DaemonSet). Читает stdout контейнеров и файлы логов RabbitMQ, добавляет хост и окружение, повторно маскирует ПДн по шаблонам (почта, телефон, номер карты) и отправляет пачками в OpenSearch по HTTPS. Буферизует на диск, если OpenSearch недоступен: логи не теряются при коротком сбое.
3. Yandex Managed OpenSearch. Тот же кластер, что для трейсов Jaeger, но с отдельными индексами и правами. Три узла в разных зонах доступности. В managed-варианте DevOps не тратит время на обновления и бэкапы.
4. OpenSearch Dashboards: поиск по `order_id`, `trace_id` и `partner_id`, дашборды ошибок по сервисам и партнёрам, плагины Alerting и Anomaly Detection.
5. Yandex Lockbox для учётной записи Fluent Bit в OpenSearch.

Схема: [c4-logging.drawio](c4-logging.drawio). Новые элементы и связи красные, системы, из которых собираем логи, обведены красной пунктирной рамкой.

### Политика безопасности логов

- В логи не пишем ФИО, телефоны, почту, адреса доставки, содержимое 3D-файлов, пароли, токены, ключи API партнёров. Покупатель, продавец, оператор и партнёр фигурируют только внутренними id. Маскирование работает в два слоя: в логгере приложения и повторно в Fluent Bit, на случай если разработчик ошибся.
- Идентификатор покупателя в логи не пишем, как и в трейсы (задание 3). По `order_id` покупателя найдёт CRM. Внутренние id продавцов, операторов и партнёров остаются. Это псевдонимизированные данные, человека по ним определяют только через справочники CRM и MES. Категорию считаю по самому чувствительному полю, поэтому логи приложений конфиденциальные. Логи безопасности (входы, IP, действия с правами) тоже конфиденциальные, но содержат больше: IP и действия сотрудников. Поэтому они лежат в отдельном индексе с более узким доступом.
- Доступ через OpenSearch Security с входом по корпоративному SSO. Роли:
  - «Поддержка»: чтение логов приложений prod, без индекса безопасности;
  - «Разработка»: чтение логов приложений всех окружений;
  - «Безопасность» (тимлид и ответственный за ИБ): чтение индекса безопасности;
  - DevOps: администрирование кластера, индексов и политик.
- Партнёры и внешние подрядчики доступа к логам не получают.
- Запись в OpenSearch только у сервисной учётки Fluent Bit, прав на чтение у неё нет. Учётки и пароли лежат в Yandex Lockbox.
- Трафик от Fluent Bit и пользователей только по TLS, кластер доступен только из внутренней сети и через VPN.
- Действия пользователей в OpenSearch (кто что искал, кто менял права) пишутся в журнал аудита OpenSearch, он хранится вместе с индексом безопасности.

### Политика хранения

Отдельный индекс на каждую систему и на каждый день: `logs-mes-api-YYYY.MM.dd`, `logs-crm-api-…`, `logs-shop-api-…`, `logs-rabbitmq-…`, плюс `logs-security-…`. Так права и срок хранения задаются на уровне системы, а старые данные удаляются целым индексом, а не по документам.

Сроки (их применяет политика ISM, аналог ILM в OpenSearch):
- логи приложений и RabbitMQ: 7 дней на быстрых дисках, ещё 23 дня на тёплых, на 30-й день индекс удаляется. Заказ идёт до трёх недель, жалобу на него разбирают в пределах месяца;
- DEBUG, если его включали на проде, отдельный индекс со сроком 3 дня;
- события заказа (создан заказ и смена статуса) дополнительно пишутся в индекс `logs-order-events-…` со сроком 180 дней. По условию клиенты ждут заказ месяцами, и жалобу на такой заказ нужно разбирать с начала его пути. Записей немного, хранить их полгода дёшево;
- логи безопасности: 30 дней в кластере, потом снапшот в S3 и хранение 1 год.

Оценка объёма (допущение, точных цифр нагрузки в условии нет). Пусть 5 000 заказов в месяц, на каждый около 50 записей по всем системам, плюс запросы партнёров в среднем 5 в секунду с записью на каждый. Запись в среднем 1 КБ.

| Индекс | Записей в сутки | Объём в сутки | Срок | Объём за срок, с репликой |
|---|---|---|---|---|
| `logs-mes-api-*` (вместе с запросами партнёров) | около 440 тыс. | 0,44 ГБ | 30 дней | около 26 ГБ |
| `logs-crm-api-*` | около 4 тыс. | 4 МБ | 30 дней | 0,3 ГБ |
| `logs-shop-api-*` | около 3 тыс. | 3 МБ | 30 дней | 0,2 ГБ |
| `logs-rabbitmq-*` | около 1 тыс. | 1 МБ | 30 дней | 0,1 ГБ |
| `logs-security-*` | около 2 тыс. | 2 МБ | 30 дней в кластере, 1 год в S3 | 0,1 ГБ в кластере, около 0,7 ГБ в S3 |
| `logs-order-events-*` | около 1,5 тыс. | 1,5 МБ | 180 дней | 0,5 ГБ |

Итого в кластере около 27 ГБ с репликой. Почти весь объём даёт журнал запросов партнёров в MES API. Если он вырастет, первым делом сократим срок для него или будем писать только ошибки и медленные запросы. Каждому дневному индексу хватает одного шарда: самый крупный, MES API, около 0,5 ГБ в сутки, это сильно меньше рекомендованных 10–50 ГБ на шард. Если через полгода объём вырастет в разы, поднимем число шардов в шаблоне индекса.

## Анализ логов: алертинг и аномалии

Сами по себе собранные логи полезны только при разборе. Чтобы они работали на опережение, настраиваю алерты в OpenSearch Alerting. Алерты уходят в Telegram-чат дежурных, критичные ещё и автозвонком:

- больше 10 записей ERROR за 5 минут в одном сервисе: дежурному. Если совпало с релизом, это повод откатить;
- любая запись о сообщении в DLX: в чат дежурных с `order_id` в тексте. Будит дежурного алерт по метрике DLX из задания 2, а этот даёт номер заказа, чтобы не искать его вручную;
- FATAL: автозвонок;
- больше 20 неудачных входов в CRM или MES с одного IP за 5 минут, или больше 50 запросов с неверным ключом API за 5 минут: ответственному за безопасность. Пока шлюза для API (инициатива И6 из задания 1) нет, IP блокируем вручную в группе безопасности Yandex Cloud, со шлюзом это будет делаться автоматически;
- расчёт стоимости дольше 30 минут: в чат команды MES, это кандидат на разбор.

Поиск аномалий нужен. Пример из условия, 4 записи о создании заказа и вдруг 10 000 за секунду, ловится как раз так. В плагине Anomaly Detection заводим детекторы:
- число событий «создан заказ» в минуту, отдельно по каждому `partner_id` и по магазину. Резкий всплеск от одного партнёра — это либо ошибка в его интеграции (повторы в цикле), либо атака. Реакция: алерт продакт-менеджеру и дежурному. Связываемся с партнёром, при атаке отзываем его ключ API. Когда появится шлюз (И6), к этому добавится автоматическое ужесточение лимита для партнёра;
- число ERROR в минуту по сервисам. Ловит медленный рост ошибок, который не дотягивает до порога;
- длительность расчёта стоимости. Если она поползла вверх, значит, растёт очередь или сложность моделей.

Детектор сначала месяц учится на нормальной картине, первые недели его срабатывания проверяем руками.

Плюс дашборды в OpenSearch Dashboards: ошибки по сервисам, заказы по статусам и источникам, запросы и ошибки по партнёрам. Их смотрим при каждом релизе.

## Дополнительно: выбор технологии

| Критерий | ELK (Elasticsearch, Logstash, Kibana) | OpenSearch | Splunk | Grafana Loki |
|---|---|---|---|---|
| Лицензия | Elastic License / SSPL, часть функций платная | Apache 2.0, всё открыто | проприетарная | AGPLv3 |
| Стоимость | бесплатно в базе, алерты и ML в платной подписке | бесплатно, есть managed в Yandex Cloud | дорогая лицензия по объёму данных в день | бесплатно, дешёвое хранение в S3 |
| Managed-сервис в нашем облаке (Yandex Cloud) | нет, разворачивать и обновлять самим | да, Yandex Managed OpenSearch | нет, свой кластер или SaaS вне РФ | нет, разворачивать самим |
| Полнотекстовый поиск и агрегации | сильные | сильные, тот же движок | сильные | слабые: индексируются только метки, по тексту перебор |
| Алерты и поиск аномалий | в бесплатной версии алерты с ограниченными каналами, отправка во внешние каналы и ML-аномалии в платной подписке | есть бесплатно (Alerting, Anomaly Detection) | есть, развитые | алерты через Grafana, аномалий нет |
| Разграничение доступа | по индексам бесплатно, по документам и полям в платной подписке | бесплатно (Security plugin) | есть | базовое |
| Хранилище трейсов для Jaeger | поддерживается | поддерживается | нет | нет, для трейсов нужен отдельный Tempo |
| Порог входа для команды | средний | средний, совместим с ELK по API и запросам | высокий, свой язык SPL | низкий, если уже есть Grafana |

Плюсы OpenSearch для нас:
- открытая лицензия, бесплатные алерты, аномалии и права доступа;
- есть managed-вариант в Yandex Cloud, где уже живут наши базы. Для команды с одним DevOps это важно;
- один кластер закрывает и логи, и трейсы Jaeger.

Минусы:
- кластер тяжелее Loki по ресурсам и стоимости хранения: индексирует весь текст;
- managed-вариант привязывает нас к Yandex Cloud. Смягчение: формат и API совместимы с Elasticsearch, переезд возможен;
- новые функции появляются чуть позже, чем в Elasticsearch.

Почему не остальные. ELK требует платной подписки ровно за то, что нам нужно: алерты во внешние каналы и поиск аномалий. Плюс у Elastic нет managed-сервиса в Yandex Cloud. Splunk слишком дорог для компании нашего размера. Loki дешевле, но слабо ищет по тексту и не умеет аномалии, а нам нужен поиск по `order_id` в произвольных сообщениях и детектор всплесков заказов.
